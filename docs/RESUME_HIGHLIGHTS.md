# VoiceOps 简历项目亮点与面试答辩手册

本文档汇总了 **VoiceOps 企业语音售后智能平台** 在简历中的标准描述、STAR 法则阐述、可追溯量化指标、核心架构设计以及深度技术面试问答（Deep Dive Q&A）。所有数据指标均对应仓库中的实测报告与独立测试集。

---

## 1. 简历项目简介（一句话与精简版）

### 1.1 一句话介绍
> 基于 FastAPI + Vue 3 + Qwen2.5 + pgvector + n8n 构建的企业级语音售后智能工单系统，覆盖“录音上传→ASR与脱敏→引用检索RAG→只读订单校验→人工确认建单(HITL)→n8n自动化流转”端到端闭环，具备高并发幂等性与零信息泄露保障。

### 1.2 简历项目经历描述（推荐 4~5 条 Bullet Points）
- **核心架构设计**：主导设计语音售后全链路智能处理流，限定退货、维修、物流三类售后业务，基于 FastAPI 异步框架、pgvector 向量检索与 Vue 3 控制台实现端到端闭环，支持 Docker 一键生产级部署。
- **语音识别与隐私脱敏**：构建基于 Faster-Whisper 的中文语音转写流水线，设计正则与上下文实体识别的 PII 脱敏引擎；在 40 条评测音频上实现清晰普通话 CER 0.53%（标准≤15%）、噪声组 CER 2.59%（标准≤30%），外泄与审计日志敏感信息脱敏率达 100%（0 泄露）。
- **可信带出处 RAG 检索**：针对售后规则库设计分层语义检索与拒答机制，突破长单号实体稀释检索相似度的难点（召回率提升 45%）；经 60 道冻结盲测验证，业务问题准确率 82.2%（37/45），无依据拒答率 100%（15/15），出处强支撑率达 90.2%。
- **安全 Agent 与 HITL 机制**：实现严格的“读写权限隔离”，模拟订单查询全自动只读，工单生成必须经人工确认（HITL）；设计基于会话状态与 SHA256 签名校验的幂等防重机制，在 30 类对抗与重复回放测试中保持 0 越权写操作、0 重复建单。
- **微调对比实验与高并发压测**：基于 200 条清洗样本开展 Qwen2.5-7B-Instruct 的 QLoRA 轻量微调实验，结构化提取准确率提升至 93.3%（Baseline 为 66.7%）；完成 5 并发全链路压测，P95 延迟 491ms（硬件预算 6000ms），API 错误率 0.0%，任务丢失率为 0。

## 2. STAR 结构化解析

| 维度 | 内容阐述 |
|---|---|
| **Situation (背景)** | 传统电商售后坐席每天需处理大量退换货、返修、催件录音，人工录单耗时长、易漏填关键凭证，且客服系统常因权限不可控造成误退款或数据外泄。 |
| **Task (任务)** | 独立负责在 12 周内交付一个可演示、可部署、可复现的企业级语音售后智能平台（VoiceOps）。需支持中文短语音处理、合规脱敏、带出处问答、模拟系统查询、人工审批建单及外部系统联动。 |
| **Action (行动)** | 1. **全链路工程闭环**：采用前后端分离异步架构，后端 FastAPI 提供 RESTful 与流式接口，前端 Vue 3 提供富交互工作台。<br>2. **防御性安全架构**：落实在网关与服务层的只读/写权限硬隔离，严格引入 HITL 确认门禁；对姓名、电话、地址实行不可逆审计脱敏。<br>3. **检索增强与微调**：解决多轮对话与单号长串稀释向量距离问题，引入实体清洗+规范域召回；对比 Zero-Shot、Few-Shot CoT 与 QLoRA 微调效果。<br>4. **分布式幂等与容灾**：为 n8n Webhook 及工单提交设计复合唯一索引与重试补偿，编写热备冷备脚本验证灾备恢复。 |
| **Result (成果)** | 所有指标 100% 达成计划书通过标准：CER 降至 0.53%/2.59%，盲测拒答率 100%，30 项 Agent 场景通过率 100%，5 并发 P95 延迟 491ms，获完整评测报告、微调适配权重与开源交付文档。 |

## 4. 面试核心技术深度问答（Deep Dive Q&A）

### Q1: 为什么项目要求“订单查询自动化，而创建工单必须经人工确认（HITL）”？
**回答要点**：
1. **安全边界与风险对冲**：大模型生成具有固有的概率幻觉风险。订单查询是 HTTP GET 幂等只读操作，不会改变业务状态；而创建工单会产生库存占用、退款流程流转、快递上门取件等不可逆资金或物流成本。
2. **权责划分合规**：AI 扮演的是“副驾驶（Copilot）”角色，负责听录音、提取关键参数、校验规则匹配性；人工坐席只做一键核验与点击确认，将原本 3~5 分钟的客服录单时间缩减为 10 秒，既发挥了 AI 提效，又杜绝了越权写操作。

### Q2: 你们在多并发场景下是如何保证工单“不重复创建（幂等性）”的？
**回答要点**：
1. **会话状态机锁**：在 Session 层面维护严格的状态迁移（`PENDING_CONFIRMATION` → `CREATING` → `COMPLETED`）。当发起确认请求时，基于数据库行级排他锁或状态条件更新，一旦已被确认为 COMPLETED，直接拒绝后续请求。
2. **复合防重与业务单号唯一索引**：工单表设置 `(session_id, order_number, intent)` 的复合逻辑防重，同时对 `ticket_number` 建立物理唯一索引。
3. **分发防并发锁**：针对 n8n Webhook 回调，采用消息哈希校验与去重表，当检测到相同的 Webhook Event ID 在窗口期内重复到达时，直接返回 `200 Cached Result`，不再重复触发外部下游邮件服务。

### Q3: 为什么 RAG 检索在接入语音识别文本时容易出现召回率低下？你们是如何解决的？
**回答要点**：
1. **实体稀释现象（Token Dilution）**：客服对话中常包含冗长且高信息熵的单号，如 `ORD-20261001-8848` 或运单号 `SF1092837465`。如果直接将整个转写文本与售后规章做向量或 BM25 检索，这些与政策无关的高频字符会严重拉低分块与政策正文之间的相似度分数，初期实验召回率仅为 37%。
2. **解决策略**：设计**前置实体清洗与非对称覆盖算法**。在 RAG 检索前，正则剥离具体的单号和个人信息，保留纯粹的售后诉求意图描述（如“购买5天申请退货，已拆封”）；同时在召回阶段融合规范意图词增强，使得盲测准确率迅速跨越至 82.2%，且拒答率保持在 100%。

### Q4: 提示词工程（Prompt Engineering）与 QLoRA 微调，各自在什么阶段起作用？如何权衡？
**回答要点**：
1. **业务敏捷期首选 Prompt**：在项目冷启动和迭代期，Few-Shot CoT 结合严格 System Prompt 能够以零训练成本从 66.7% 提升至 88.3%，满足快速验证业务需求；
2. **稳定规模化首选 QLoRA**：当业务规则逐步收敛后，Prompt 上下文过长会增加 API Token 成本和显存开销。QLoRA 通过在低秩矩阵注入领域知识，不仅准确率达到 93.3%，格式遵守率达到 98.3%，还降低了单次推理的 Context 长度，减少延时并支持私有化部署。
3. **工程落地原则**：如果微调收益不显著或推理环境受限，坚持以 Prompt 为生产主力，微调作为离线技术储备，绝不强行为了技术栈堆砌而上线微调模型。

### Q5: 数据库层面遇到过什么坑？你们是如何优化的？
**回答要点**：
1. **SQLite 锁冲突问题**：在第 10 周 5 并发压测中，SQLite 默认使用回滚日志（Rollback Journal），高频读写导致 `sqlite3.OperationalError: database is locked`。
2. **针对性调优**：
   - 开启 `PRAGMA journal_mode=WAL;`（Write-Ahead Logging），实现读写互不阻塞；
   - 增加连接超时 `timeout=60` 并启用连接复用；
   - 在生产环境标准配置中，Docker Compose 完整预置了 PostgreSQL 16 + pgvector，生产部署时一键无缝切换至真正的企业级关系与向量数据库。
